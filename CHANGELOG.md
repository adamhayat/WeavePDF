### Fixed — V1.0104: edits stay where the user placed them on Canva-style PDFs (MediaBox y0 offset) (2026-05-20)
- Adam edited `test.pdf` (downloaded from Canva): he changed the date in the top right and added his signature, title, and name to the bottom. In WeavePDF the placements looked correct. After Save → Close → Reopen, the date whiteout left the top half of the original date visible and the signature/title/name sat ~10–14pt below where he placed them.
- **Root cause.** Canva exports PDFs with `MediaBox [0, 7.83, 595.5, 850.08]` — the page's lower-left corner is at user-space y=7.83, not y=0. The PDF spec allows any MediaBox origin. WeavePDF captures all overlay positions MediaBox-relative (i.e. (0, 0) = lower-left of the visible page) because that's what the click→PDF conversion in [PageCanvas.tsx](src/renderer/components/Viewer/PageCanvas.tsx) yields. Every pdf-lib baker in [pdf-ops.ts](src/renderer/lib/pdf-ops.ts) — `drawText`, `drawWrappedText`, `whiteoutRegion`, `placeImage`, `drawHighlight`, `drawRect`, `drawCircle`, `drawLine`, `drawArrow`, `drawPath`, `drawStickyNote`, `drawHeaderFooter`, `drawBatesNumbers`, `drawTextWatermark`, `applyOcrTextLayer` — passed those coords straight into pdf-lib, which treats them as raw user-space. Result: every baked edit landed `mediaBox.y` pts low. While editing, on-screen positioning used the same wrong axis on both sides of the equation so it looked correct; the discrepancy only surfaced after the bake left the renderer.
- **Fix.** New `pageContentOrigin(page)` helper in [pdf-ops.ts](src/renderer/lib/pdf-ops.ts) reads `page.getCropBox()` (which falls back to the MediaBox, matching what pdf.js renders). Every coord-consuming bake call now adds `origin.x, origin.y` to its inputs. Stored MediaBox-relative metadata stays the same shape — only the bake boundary translates. Round-trip is symmetric because the whiteout returned in `BakedBBox` is also MediaBox-relative, so the next save re-applies the same offset.
- **Auxiliary bakers patched in the same pass.** `drawHeaderFooter`, `drawBatesNumbers`, `drawTextWatermark`, and `applyOcrTextLayer` use `page.getSize()` + a margin/center anchor; they now also add the CropBox origin so their visible positions stay relative to the visible page edge instead of the MediaBox-(0,0) anchor.
- **Tests.** [tests/e2e/v1.0104-mediabox-offset-bake.spec.ts](tests/e2e/v1.0104-mediabox-offset-bake.spec.ts) — both specs (text bake + image bake on a fixture with `MediaBox [0, 10, 612, 802]`) pass post-fix and fail pre-fix because pdf-lib drops the text at y=100 and the image at y=200 instead of y=110 / y=210. New fixture `sample-offset-mediabox.pdf` generated by [scripts/generate-fixtures.mjs](scripts/generate-fixtures.mjs). `npm run typecheck` green. `npm run package:test` green.
- **Files touched:** [package.json](package.json), [src/renderer/lib/pdf-ops.ts](src/renderer/lib/pdf-ops.ts), [scripts/generate-fixtures.mjs](scripts/generate-fixtures.mjs), [tests/e2e/v1.0104-mediabox-offset-bake.spec.ts](tests/e2e/v1.0104-mediabox-offset-bake.spec.ts).

### Fixed — V1.0094: app froze within seconds of opening any PDF — infinite re-render loop in the sidebar thumbnail effect (2026-05-14)
- Adam: "app is totally unstable, you can use it for maybe a few seconds and then it totally stops responding. Happens every time I open it and try to edit text, sometimes even without editing."
- **Root cause.** V1.0090's "show pending overlays on thumbnail" feature in [Sidebar.tsx](src/renderer/components/Sidebar/Sidebar.tsx) computed `pendingText = tab.pendingTextEdits.filter(...)` (and same for image + shape) **inline during render**, then used those arrays as `useEffect` deps for the pdf.js page render. Inline `.filter()` returns a NEW array reference every render, so React's `Object.is` saw "changed" deps and re-ran the effect every time. With pdf.js's single-threaded worker, dozens of canceled-and-restarted page renders queue up and the main thread freezes.

Zustand updates immutably — the array ref only changes when the user actually adds/edits/removes an overlay — so the effect now fires only when there's real work to do.

### Changed — V1.0093: doc → PDF conversion routes through Pages.app first for Word-fidelity output (embedded Calibri, exact margins, line spacing) (2026-05-14)
- Adam: "Can you make sure the PDF is exactly the same as the doc in formatting? You know when on word and you export as PDF it keeps the word formatting? Right now the PDF is very different formatting, spacing etc."
- **Root cause.** V1.0092's pipeline (`textutil → HTML → printToPDF`) produced generic reflowed output: textutil's HTML export uses Helvetica fallback, ignores most Word styling (line spacing, paragraph spacing, font weights, tables), and the BrowserWindow re-renders with HTML defaults. ### Changed — V1.0088: 1-up print path is content-aware + auto-rotates (scale fit-fill + landscape rotation) (2026-05-13)
- Adam reported two bugs in V1.0085/V1.0087's print preview: (1) Sliding Scale above 100% didn't make content take more of the page — it scaled outside the page bounds and got clipped. (2) Picking Landscape resized the output sheet but the source still rendered at portrait orientation, leaving empty space on the right of the page.
- **Root cause.** V1.0085's `scalePageContent` kept the output page sized identical to the source page and drew the scaled content centered. At scale > 100% the oversized content overflowed and clipped at the page edge. Separately, no path in the 1-up pipeline rotated source content to match a chosen orientation — `fitToPaper` only scaled to fit, never rotated, so a portrait scan on a landscape sheet was sized to the height (= small) with whitespace on the right.
- **Fix — new `scaleToFitForPrint(bytes, paper, orientation, scalePct)` in [pdf-ops.ts](src/renderer/lib/pdf-ops.ts).** All-raster (pdf.js → embedPng), same V1.0086/V1.0087 pixel-scan helper. Per source page:
  1. Rasterize at 1.5× DPI.
  2. Detect content bbox (white threshold 240, 6px pad).
  3. Auto-rotate the cropped canvas 90° if the content's landscape-ness differs from the sheet's. This matches Acrobat's "Auto portrait/landscape" and macOS Preview's auto-rotation — a portrait scan on a landscape sheet rotates so its long edge aligns with the sheet's long edge.
  4. Compute fit-fill scale: `fitScale = min(printable_w / content_w, printable_h / content_h)`. Multiply by `scalePct / 100` to get the user's effective scale. At 100% the content fills the printable area at its largest size while preserving aspect; <100% shrinks within the page; >100% overflows margins toward page edge.
  5. Compose centered on an output page sized to `paper` + `orientation`.
- **Behavior change.** For full-page typeset docs (typical letter PDF with content filling the printable area), fit factor ≈ 1.0 — scale 100% renders at the same size as before, no visible difference. For sparse-content docs (scans, certificates, the vehicle permit Adam attached), content auto-zooms to fill the page at scale 100% — the entire point of the fix. Slider above 100% is now a "more zoom" affordance that overflows margins (and eventually clips at page edge if pushed far past the fit factor).
- **Pipeline wiring** in [PrintPreviewModal.tsx](src/renderer/components/PrintPreviewModal/PrintPreviewModal.tsx):
  - `layout === "fit"` → unchanged (V1.0086 `fitAllOntoSingleSheet`).
  - `layout > 1` (n-up) → unchanged (legacy `scalePageContent` + `nUpPages`).

### Added — V1.0072: round-trip editability — saved text overlays reopen as pending edits (2026-05-12)

  - [document.ts](src/renderer/stores/document.ts) — `commitAllPendingTextEdits` accumulates a `WeavePdfTextEdit[]` payload and calls `embedWeaveMetadata` after the bakes. New `restorePendingTextEdits` action bulk-inserts overlays without snapshotting / dirtying.

### Fixed — V1.0060: text drag-resize is smooth + proportional (2026-05-12)
- **V1.0058's text resize was jumpy.** Adam: "Resizing is very fast and jumpy, not easy to use." Two root causes in [PendingTextLayer.tsx](src/renderer/components/Viewer/PendingTextLayer.tsx):
  1. **Axis flip-flop.** The handler picked `delta = max(|dx|, |dy|)` *per frame*, so on diagonal drags the selected axis flipped between dx and dy every few pixels — the font size oscillated visibly as the user moved the cursor.

- **Fix: proportional scaling from a fixed anchor.** Capture the wrapper's top-left corner in CSS pixels at gesture start. Record `startDist = hypot(cursorX − anchorX, cursorY − anchorY)`. On every move event compute `newDist` the same way and apply `newSize = startSize × (newDist / startDist)`. `newDist` is a continuous function of cursor position, so there's no axis-pick flip-flop and no per-frame jitter. Sensitivity self-calibrates: the same drag distance produces a similar *proportional* change regardless of starting font size (16pt → 32pt vs 30pt → 60pt both happen with roughly the same drag distance). Clamp to [6, 144] like the +/- buttons. Tiny `startDist < 1` guard prevents the divide-by-zero edge.
- **Result:** drag 60px past the corner → text roughly doubles. Drag back → snaps smoothly back to original. No oscillation on diagonal moves. Matches Photoshop's free-transform corner-handle behavior for proportional scaling.

### Fixed — V1.0054: print no longer outputs blank pages (2026-05-08)
- **Blank-print bug.** User reported "When i try to print a document, it comes out blank and doesnt print." Reproduced live: ⌘P → Print Preview rendered the doc correctly → click Print → modal closes (`webContents.print()` resolves with success) → physical printer outputs blank pages. End result: real-printer output is blank pages.

- **Side-benefit:** the elaborate `webRequest.onBeforeRequest` filter, `setPermissionRequestHandler`, and per-print partition that hardened the hidden BrowserWindow are all gone — `lp` doesn't load JS or AcroForm scripts, so a malicious PDF can't phone home through the print path.

### Added — V1.0052: Edit Text falls back to OCR on image-only PDFs (2026-05-07)
- **Edit Text now works on scanned / image-only PDFs.** User asked: can we edit text in PDFs where the "text" is rasterized into a screenshot (e.g. an Instagram screenshot dropped into a Merged PDF, a scanned receipt, a photo of a contract)? ### Added — V1.0013: stable self-signed code-signing identity replaces ad-hoc (ends per-rebuild Keychain prompts) (2026-04-29)
- **Stops the per-rebuild Keychain "Always Allow" prompt.** Previously, every `npm run package` produced a new ad-hoc-signed binary with a unique CDHash, and macOS Keychain pinned the safeStorage signature item's ACL to that hash. Each rebuild's CDHash wasn't on the allowlist → Keychain prompted; "Always Allow" only added the current CDHash, so the *next* rebuild prompted again. With a stable signing identity, the binary's designated requirement includes "signed by this specific key" — the requirement stays the same across rebuilds, so the Keychain ACL accepts new builds silently after one "Always Allow."
- **New script** [scripts/setup-local-signing.sh](scripts/setup-local-signing.sh) — idempotent. Creates a 10-year self-signed code-signing certificate (CN=`WeavePDF Local`, EKU=`codeSigning`) in the user's login keychain via `openssl req -x509` + `openssl pkcs12 -export -legacy` + `security import -A`. The `-legacy` flag is critical: OpenSSL 3.x's default AES-256 PBKDF2 ciphers aren't readable by macOS's `security import` (fails with `MAC verification failed`); legacy RC2/3DES is what the Security Framework supports.
- **Forge auto-detects the identity.** [forge.config.ts](forge.config.ts) calls `security find-identity -p codesigning` at build start, looks for `"WeavePDF Local"`, and uses that as the signing identity if found. Falls back to ad-hoc (`-`) when the identity isn't installed, so the build doesn't break for someone who hasn't run the setup script. Identity is propagated to the postPackage hook (re-signs the parent .app) and to `scripts/build-finder-sync.mjs` via the `WEAVEPDF_SIGN_IDENTITY` env var (signs the .appex).
- **Detection skips the strict `-v` filter** because self-signed certs report `CSSMERR_TP_NOT_TRUSTED` (the `-v` flag is for Apple-CA-anchored identities like Developer ID). `codesign` itself accepts the untrusted self-signed cert without issue — the trust check is only enforced by `find-identity -v`, not by signing.
- **Re-sign of the parent .app stays without `--deep`** — preserves the inner `.appex`'s sandbox entitlements (codesign --deep would re-sign the .appex without entitlements, and pkd would reject it with "plug-ins must be sandboxed").
- **Distribution caveat documented:** the `WeavePDF Local` cert lives only on the developer's Mac. Recipients of the DMG still get the Gatekeeper "from an unidentified developer" warning on first install — same as ad-hoc — because the cert isn't from a CA Apple knows. They DO get a parallel benefit: future updates signed with the same cert won't re-prompt them in Keychain. For full no-warning distribution: Apple Developer ID ($99/yr) + `xcrun notarytool submit`.
